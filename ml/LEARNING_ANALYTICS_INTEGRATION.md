# Learning Analytics V1 · Prediction Core 통합 준비

이 설계는 [Prediction Core V1 PR #11](https://github.com/studio-lucky7/neuroknot/pull/11)의
`cdf7e87`을 읽기 전용으로 검토한 결과다. 아래 통합 API와 저장 계약은 병합 후 구현 대상이다.
현재 테스트는 `develop`에 있는 Elo 공개 API만 사용한다.

## Elo 상태 소유권

현재 `LearningHistory`는 자체 `EloModel`을 만들고 카탈로그와 온보딩 prior를 등록한다.
서버 채점 결과를 받으면 최초 유효 답안만 갱신하고, 노출·제출·종료 기록과 중복 판정 상태도 소유한다.
Core의 `select_passage()`는 호출자가 넘긴 모델의 `predict()`와 `user_rating()`을 읽고,
`register_passage()`는 호출자가 넘긴 Elo 모델에 문항을 등록한다.
별도 인스턴스로 운영하면 Analytics가 기록한 θ와 공유 문항 난이도가 추천에 즉시 반영되지 않는다.

| 방식 | 효과와 비용 |
| --- | --- |
| 동일 가변 모델을 두 컴포넌트에 주입 | 인스턴스를 맞추기 쉽다. 양쪽에 갱신·등록 권한이 있으면 감사 기록 없는 쓰기, 이중 갱신, 추천 중 상태 혼합이 생길 수 있다. |
| 단일 소유자와 읽기 전용 선택기 | 학습 처리 서비스가 Elo와 이벤트 커서를 함께 소유한다. 답안 갱신과 카탈로그 등록은 이 경계로 들어온다. Core 선택기에는 읽기 전용 모델과 같은 커서에서 만든 이력을 제공한다. |

두 번째 방식을 권장한다. 병합 후 `LearningHistory`를 이 소유자 아래에 두고, 후보 평가는
한 커서에 고정된 읽기 뷰에서 수행한다. `seen_passage_ids`와 `seen_item_ids`는 실제 노출,
`skill_attempts`는 최초 유효 제출에서 같은 커서까지 계산한다. 선택 계산과 실제 노출 저장은
별도 단계다. 선택과 노출 사이의 동시 요청에서 중복 제공을 막으려면 저장 경계에서 노출 이력을
다시 확인하거나 예약을 직렬화해야 한다.

## 체크포인트와 재시작 계약

`to_state()`는 설정·K 스케줄, 온보딩 prior, θ와 문항 난이도, 각 갱신 카운터, 문항 스킬을 저장한다.
`from_state()`는 이를 새 Elo 모델로 복원한다. 이벤트 ID, 제출 ID, 최초 응답 판정, 노출별 답안,
종료 상태와 분석용 레코드는 이 스냅샷 밖에 있다.

체크포인트의 식별자는 `checkpoint_version`, `stream_id`, `through_sequence`,
`model_revision`, `catalog_revision`, `onboarding_revision`이다. 같은 커서의 한 저장 경계에서
다음 상태를 읽을 수 있어야 한다.

| 저장 항목 | 복구에 필요한 이유 |
| --- | --- |
| Elo 스냅샷 | 해당 순번까지의 θ, b, K 카운터와 모델 설정을 복원한다. |
| 수락한 이벤트와 영수증 | 정규화된 페이로드 또는 검증 가능한 다이제스트, `event_id` 및 별칭, 논리 키와 원본 레코드의 연결을 보존한다. 논리 키는 노출 ID, 제출 ID, 노출별 종료 ID를 유형별로 구분한다. |
| 원본 처리 결과 | 최초 답안의 예측과 전후 θ·b, 재시도 결과, 노출 및 종료 레코드를 보존한다. 재전송에는 현재 Elo로 예측을 다시 계산하지 않고 원래 결과를 반환한다. 분석의 과거 시계열도 이 기록을 사용한다. |
| 인과 상태 | 버전 문항별 사용자 최초 응답, 노출의 문항별 응답 여부와 종료 상태가 필요하다. 체크포인트 투영에서 읽거나, 보존한 원본 레코드로 `through_sequence`까지 다시 만든다. |

1. 체크포인트와 커서까지의 로그가 같은 스트림·설정에 속하는지 확인한다. 앞부분의 영수증과
   인과 상태는 저장된 레코드로 복원하며, 이 구간에서는 Elo `update()`를 호출하지 않는다.
2. `from_state()`로 Elo를 복원한 뒤 `sequence > through_sequence`인 로그만 적용한다.
   빠진 순번이나 커서 불일치는 복구를 중단한다. 원본 이력과 초기 설정이 모두 있으면
   초기 모델부터의 전체 재생을 대안으로 사용한다.
3. 요청을 처리할 때 순번을 발급하기 전에 ID와 논리 키를 검사한다. 같은 ID와 동일한 내용은
   기존 결과를 반환하고, 같은 키에 다른 내용은 충돌로 거부한다. 동일 제출에 새 이벤트 ID가
   붙으면 원래 결과를 참조하는 별칭 영수증을 기록한다. 별칭은 Elo·집계에 영향을 주지 않는다.
4. 신규 이벤트·영수증·처리 결과 및 모델 적용 커서의 저장 경계를 원자적으로 관리한다.
   구현 시 내구성 있는 전역 로그를 기준으로 모델을 재구성할 수 있어야 하며, 영수증이나
   커서가 저장되기 전에 성공을 응답하지 않는다. 메모리 변경 뒤 트랜잭션이 실패하면
   해당 모델 뷰를 폐기하고 마지막 커밋 경계에서 복구한다.

예를 들어 제출이 순번 100에서 적용되고 응답 전 프로세스가 종료돼도, 재시작 후 같은
제출 ID는 순번 100의 원본 결과를 반환한다. 체크포인트가 100이면 101부터 갱신한다.
이 보장은 영수증과 최초 응답 키의 보존 범위에 의존한다. 오래된 요청의 재전송을 계속
받으려면 그 키와 원본 결과를 보존하거나, 보존 경계 이전 요청을 명시적으로 거부해야 한다.

## 전역 순서와 시간대

현재 V1은 신규 이벤트가 이전 시각보다 빠르면 거부하고, 재생 시 UTC 시각으로 안정 정렬한다.
동일 시각에 두 사용자가 같은 문항을 풀면 입력 배열 순서에 따라 두 번째 예측과 최종 b가 달라진다.
통합 시에는 한 Elo 상태를 공유하는 스트림마다 서버가 확정한 `sequence`를 사용한다.
동시각 이벤트에 대한 회귀 테스트는 현재 V1에서 외부 순번으로 정렬한 경우만 검증한다.
서로 다른 시각의 이벤트가 순번과 반대로 들어오는 경우에는 기존 재생 정렬을 그대로 쓸 수 없다.

| 구분 | 계약 |
| --- | --- |
| 중복 판정 | 이벤트 ID와 논리 키, 정규화된 페이로드로 결정한다. 시간이나 순번의 동일 여부를 중복 근거로 쓰지 않는다. |
| 모델 적용·재생 순서 | 서버가 이벤트 또는 새 별칭을 수락할 때 스트림의 다음 로그 순번을 확정한다. 잠금 또는 단일 작성자로 커밋 순서를 직렬화한다. 중복 재전송에 새 순번을 부여하지 않는다. 노출은 제출보다, 제출은 해당 종료보다 먼저 확정돼야 한다. 순번은 커밋된 로그에서 연속이어야 한다. |
| 분석 시각 | 활동은 서버가 확정한 `occurred_at`을 사용자 IANA 시간대로 변환해 현지 날짜에 집계한다. θ 시계열은 모델 순번과 서버의 단조 비감소 `applied_at`을 사용한다. 두 시각은 UTC로 저장한다. |

순번은 이벤트 V1 페이로드 외부의 저장 봉투에 둔다. JavaScript의 안전 정수 범위를 넘길 수 있는
순번은 JSON에서 십진 문자열로 전달하고 저장소에서는 정수로 비교한다.
늦게 도착한 신규 이벤트가 현재 노출·종료 상태와 양립하면 수락 순번의 끝에서 처리한다.
이미 종료된 노출에 대한 신규 제출처럼 인과관계를 위반하는 경우에는 명시적으로 거부한다.
과거 시점의 θ를 재계산하려면 별도의 통제된 전체 재생을 수행한다.

리포트는 조회한 `through_sequence`를 고정한다. `as_of` 시점까지 적용된 레코드만 조회하고,
활동 건수는 그중 `occurred_at <= as_of`인 기록을 현지 날짜에 배치한다. θ의 주간 경계는
`applied_at`을 사용한다. 현재 `analyze_user()`의 `occurred_at` 기준 조기 종료는
시간순 저장을 전제로 하므로, 순번 기반 구현에서 그대로 유지하면 늦게 들어온 과거 활동을
빠뜨릴 수 있다.

## 문항·버전 연결 계약

| 공통 메타데이터 | Core | Analytics |
| --- | --- | --- |
| 버전별로 고유한 `item_id`와 스킬 | `PassageCandidate.questions`의 문항 ID와 스킬 | `CatalogItem.item_id`, `skill` |
| 불변 문항 버전 | Core 후보에는 별도 버전 필드가 없으므로 호출자 카탈로그에서 ID와 연결한다. | `CatalogItem.item_version`과 제출 필드를 일치시킨다. |
| 지문 및 퀴즈 버전 | 후보의 `passage_id`와 카탈로그의 퀴즈 버전·문항 목록 | 실제 노출의 `passage_id`, `quiz_version`, `item_ids` |
| 초기 난이도 | `register_passage()`는 문항별 별점, 지문 힌트, 중립값 순으로 적용한다. | 같은 유효 별점을 `CatalogItem.difficulty`에 기록한다. 중립 fallback은 `None`이다. |

초기값의 출처와 유효 별점을 카탈로그에 고정하고, 복구 시 같은 prior 매핑을 사용한다.
문항의 내용·채점·스킬 버전이 바뀌면 새 문항 ID를 발급한다. 스냅샷 복원 후 기존 ID의
등록 요청은 스킬·버전을 확인하고 현재 b와 풀이 횟수를 유지한다. 새 ID만 초기화한다.
Core의 `register_passage()`는 기존 ID의 스킬 불일치를 거부하지만 버전은 호출자가 확인해야 한다.
기존 `EloModel.register_item()`은 같은 ID의 b를 유지하면서 스킬 매핑을 바꿀 수 있으므로,
연동 계층에서 ID·버전·스킬을 검증한 뒤 호출한다.

## PR #11 병합 후 검증 순서

1. 최신 `develop`과 병합 차이를 점검하고 README와 의존성의 양쪽 내용을 보존한다.
2. 단일 소유자와 등록 어댑터를 연결한다. 명시 별점·힌트·중립 prior, 동일 ID 재등록,
   스킬·버전 충돌, 선택기의 동일 커서 이력 사용을 실제 Core API로 테스트한다.
3. 실제 `to_state()`/ `from_state()`로 **전체 재생과 체크포인트+이후 재생**의
   예측·θ·b·카운터·과거 리포트를 비교한다. 커밋 전후 중단, 응답 전 종료 후 재전송,
   오래된 별칭·충돌, 커서 누락과 설정 불일치도 포함한다.
4. 순번 기반으로 동시각 공유 문항 답안, 역순 전달, 시간은 늦게 도착한 과거 활동,
   서울 자정 경계와 순번 간격 검증을 실행한다. 이어 두 모듈의 전체 테스트와 실험을 재실행한다.
