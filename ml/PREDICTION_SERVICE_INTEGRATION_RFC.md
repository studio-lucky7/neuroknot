# Prediction 서비스 연동 RFC

상태 **팀 리뷰 초안** · 워크플로 기준 `bb0a00c` · FastAPI 기반 참고 [PR #12](https://github.com/studio-lucky7/neuroknot/pull/12)의 `7cc1d9d`

범위는 Python 워크플로를 FastAPI·MySQL에 연결하는 계약이다. 아래의 **현재**는 기준 커밋의 구현과 기존 테스트를, **Prediction 후속**은 이 슬라이스에서 구현할 수 있는 안을, **팀 합의**는 공통 계약이나 제품 정책을 뜻한다. 기존 검증 범위는 프로세스 내 실행과 체크포인트 복원이다. DB 다중 워커와 HTTP 계약의 검증 기준은 §10에 둔다.

## 1. 공개 메서드와 HTTP 매핑

**현재.** [PredictionService](neuroknot_ml/service_workflow.py)가 단일 `LearningHistory`를 사용한다. 추천은 읽기 전용이며 노출 확정 때 공개 퀴즈를 반환한다. 답안은 서버가 채점하고 사용자·문항의 첫 유효 답안만 Elo를 갱신한다. 완료는 세 문항 모두의 유효 답안을 요구한다. 오답도 유효 답안이다.

**Prediction 후속.** 아래 경로와 응답은 제안이다. 라우터에서 허용 필드를 명시하고 서버가 사용자와 시각을 결정한다. `sequence`와 `through_sequence`는 JavaScript 정수 정밀도를 고려해 10진 문자열로 제공한다.

| 우선순위 | Python 공개 메서드 | 요청 → 응답 초안 |
| --- | --- | --- |
| 필수 | `recommend(user_id)` | `GET /prediction/next` → 200, `through_sequence`와 `quiz`의 지문 ID·버전만 반환. 소진 시 `quiz: null`. Python 응답의 본문·문항은 이 단계에서 제외한다. |
| 필수 | `confirm_exposure(...)` | `POST /prediction/exposures`에 `exposure_id`, `passage_id`, `quiz_version` → 200, `exposure_id`, `sequence`, 공개 `quiz` 전체. 같은 요청 재전송은 원래 응답을 반환한다. |
| 필수 | `submit_answer(...)` | `POST /prediction/submissions`에 `exposure_id`, `item_id`, `submission_id`, `choice_index` → 200, `submission_id`, `is_correct`, `is_retry`, `sequence`. |
| 필수 | `complete_learning(...)` | `POST /prediction/exposures/{exposure_id}/complete`, 요청 본문 없음 → 200, `exposure_id`, `status: completed`, `sequence`. |
| 필수 | `analyze(user_id, *, as_of, timezone_name)` | `GET /prediction/analytics?as_of=…&timezone=Asia%2FSeoul` → 200, `summary`, `weekly`, `skills`, `through_sequence`. 기준 시각 생략 시 서버가 UTC 현재 시각을 고정한다. 기존 리포트의 `as_of`와 `timezone`도 응답에 유지한다. |
| 운영 필수 | `register_quiz(generated, *, quiz_version, passage_body, item_difficulties)` | 검수·출판 경계의 내부 호출. 초기에는 서비스 내부 어댑터나 운영 명령으로 등록한다. |
| 운영 필수 | `checkpoint()` / `from_checkpoint(state)` | 내부 저장·복원 작업. 복원 입력에는 채점 키와 제출 선택값이 포함된다. |

노출 응답의 `quiz`는 `passage_id`, `quiz_version`, `passage_body`, `questions`만 포함하며 각 문항은 `item_id`, `stem`, `options`를 제공한다. 배열은 서버에 보관한 슬롯과 선택지 순서를 따른다. 다음은 같은 학습의 요청과 응답 일부다.

```json
{
  "next_response": {"through_sequence":"20","quiz":{"passage_id":"p1","quiz_version":"v2"}},
  "exposure_request": {"exposure_id":"x1","passage_id":"p1","quiz_version":"v2"},
  "exposure_response": {"exposure_id":"x1","sequence":"21","quiz":{
    "passage_id":"p1","quiz_version":"v2","passage_body":"예시 본문",
    "questions":[
      {"item_id":"q-5e49effe702b0d1c5dbaca7ba076e70607f9e54e23a30d9378a21e529e9bfad5","stem":"예시 질문 1","options":["A","B","C","D"]},
      {"item_id":"q-861d91c4e74811853270e947b39cbd048b7eca1eedfcd0e0371691422ae01fa5","stem":"예시 질문 2","options":["A","B","C","D"]},
      {"item_id":"q-0757f019c9b182503268c1e044a86d0ef1abf3195318d927baaa19be3f0d5ed1","stem":"예시 질문 3","options":["A","B","C","D"]}
    ]
  }},
  "submission_request": {"exposure_id":"x1","submission_id":"s1","item_id":"q-5e49effe702b0d1c5dbaca7ba076e70607f9e54e23a30d9378a21e529e9bfad5","choice_index":0},
  "submission_response": {"submission_id":"s1","is_correct":false,"is_retry":false,"sequence":"22"},
  "completion_response": {"exposure_id":"x1","status":"completed","sequence":"25"}
}
```

**팀 합의.** API 버전·경로, 재전송 시 200 응답, 앱이 재사용할 노출·제출 ID 발급 방식, 분석 응답의 범위·필드 및 시각 정책을 확정한다. 기본안은 앱이 명령마다 불투명 ID를 한 번 생성해 재전송에도 유지하고, 계정 ID는 인증 문맥에서 취하는 방식이다.

## 2. 데이터 관계와 고유성

**현재.** 퀴즈는 `(passage_id, quiz_version)`로 보관한다. 문항 ID는 해당 키와 0부터 시작하는 문항 슬롯을 SHA-256으로 해시한 `q-` 접두사 ID다. `item_version`은 퀴즈 버전과 같고, 이전 노출은 확정된 버전으로 계속 채점된다. 같은 버전의 같은 등록은 재사용되며, 학습된 문항 난이도는 유지된다.

**Prediction 후속.** 다음은 물리 테이블명과 공통 FK를 확정하기 전의 논리 모델이다.

| 레코드 | 관계와 권장 제약 |
| --- | --- |
| 사용자·지문 | 팀 공통 사용자·콘텐츠 키를 참조한다. 하나의 지문에는 여러 불변 퀴즈 버전이 있으며 활성 버전 포인터는 지문당 하나다. |
| 퀴즈 버전·문항 | `UNIQUE(passage_id, quiz_version)`, `UNIQUE(quiz_release_id, slot)`, `UNIQUE(item_id)`. 본문·문항·선택지 순서·채점 키가 바뀌면 새 버전을 출판한다. 버전에 3개 문항과 고정된 표시 순서를 검증한다. |
| 노출 | 사용자와 특정 퀴즈 버전을 연결한다. `UNIQUE(stream_id, exposure_id)` 및 V1의 `UNIQUE(stream_id, user_id, passage_id)`. 활성 버전이 바뀌어도 이전 노출의 버전은 유지한다. |
| 답안·최초 풀이 | 한 노출에 여러 제출이 속한다. `UNIQUE(stream_id, submission_id)`, 노출의 퀴즈 버전과 문항 소속 일치, 노출 사용자 일치. 별도 최초 풀이 행의 `UNIQUE(stream_id, user_id, item_id)`로 최초 제출을 연결한다. 제출 전체에는 이 제약을 적용하지 않아 유효 재시도를 보존한다. |
| 완료 | 노출과 0 또는 1개 완료가 연결된다. `UNIQUE(stream_id, exposure_id)`로 완료를 고정하고 해당 버전의 서로 다른 세 문항에 제출이 있는지 검사한다. |
| 이벤트·처리 영수증 | `UNIQUE(stream_id, sequence)`, `UNIQUE(stream_id, event_id)`. 영수증은 동작별 불투명 ID, 인증 주체, 정규화 요청, 원본 응답을 이벤트와 연결한다. |
| Elo·체크포인트 | 같은 카탈로그를 학습하는 사용자들이 한 모델 스트림의 문항 난이도를 공유한다. 체크포인트는 해당 스트림의 학습 커서와 카탈로그·온보딩 버전을 함께 고정한다. |

버전·문항 소속은 가능하면 복합 FK로 보장하고, 세 문항 완료처럼 여러 행을 읽어야 하는 조건은 동일 트랜잭션에서 검증한다. 최초 풀이와 노출에 사용하는 ID의 대소문자·길이 비교 규칙은 Python과 DB에서 일치시킨다.

**팀 합의.** 사용자·지문의 실제 소유 테이블, 식별자 규격, 삭제·보존과 FK 정책, 지문 재학습 허용 시점을 확정한다. 추천 기본안은 현재처럼 버전이 바뀌어도 같은 지문의 재노출을 막는 것이다.

## 3. Elo·이벤트·체크포인트 복구 계약

**현재.** [LearningHistory](neuroknot_ml/learning_history.py)가 Elo 상태를 소유한다. 내부 체크포인트에는 `checkpoint_version`, `model_revision`, `stream_id`, `through_sequence`, `model`, 카탈로그와 온보딩 설정·리비전, 이벤트 및 원본 판정 이력이 담긴다. Elo 상태에는 prior, θ, b, 횟수 및 K 설정이 들어간다. 서비스 체크포인트 `{version, history, quizzes, choices}`가 이를 감싸며 퀴즈 등록 순서·버전별 채점 키와 제출의 실제 선택값을 보존한다. 이 구조는 원본 응답과 최초 풀이 판정의 복원을 지원한다. 내부 엔진은 후속 이벤트 재생을 지원하지만, 서비스에는 카탈로그와 영수증까지 함께 복구하는 공개 후속 재생 인터페이스가 없다. [엔진 통합 계약](LEARNING_ANALYTICS_INTEGRATION.md)

**Prediction 후속.**

1. 한 공유 모델 스트림에서 서버가 연속 `sequence`를 발급한다. MySQL의 저장 타입은 엔진 범위에 맞춘 signed `BIGINT`, 외부 표현은 문자열을 권장한다. `occurred_at`은 UTC로 정규화한 학습 시각이며 주간·스트릭 집계에 쓴다. `applied_at`은 서버가 정한 모델 적용 시각이며 앞 순번과 `occurred_at`보다 이르지 않게 한다. 실제 DB 커밋의 벽시계 시각과는 별개다.
2. 이벤트·영수증·출판 기록을 내구 저장한다. 카탈로그 활성화는 학습 이벤트 순번을 소비하지 않으므로, 별도 출판 순서/리비전과 해당 경계를 기록한다. 퀴즈 출판이 개입된 구간도 그 당시 버전과 prior로 재생할 수 있어야 한다. 온보딩도 적용한 리비전을 보존한다.
3. 체크포인트는 일관된 커서에서 봉인한다. 서버 전용 저장 위치에 스키마·모델 버전, 스트림, 순번, 카탈로그·온보딩 리비전, 체크섬을 함께 기록한다. 모델 스냅샷을 복원한 뒤 그 순번까지의 영수증과 최초 풀이·노출·완료 상태를 복구한다. 이미 스냅샷에 반영된 이벤트는 Elo에 다시 적용하지 않는다.
4. 같은 경계의 출판 기록과 순번이 더 큰 승인 이벤트만 재생한다. 순번 공백, 버전·스트림 불일치, 누락된 영수증·채점 키는 복구 오류로 처리한다. 이전 유효 체크포인트와 보관 로그가 있으면 그 경계부터 복구한다. 정상 복구와 헤드 대조가 끝난 상태만 읽기·쓰기에 공개한다.
5. 초기 내구화는 승인 쓰기마다 **전체 서비스 체크포인트**와 이벤트·영수증을 함께 커밋하는 방안을 권장한다. 규모를 제한한 통합 검증에 맞는 방식이다. 전체 이력을 담는 현 형식은 장기 쓰기 비용이 크므로, 주기 스냅샷으로 전환하려면 서비스 수준의 재생 어댑터를 먼저 만들고 선택값·출판 이력까지 함께 복원한다. 엔진 이벤트만 재생하면 서로 다른 두 오답 선택값을 구분할 정보가 부족하다.

분석 읽기는 하나의 커서와 `as_of`로 고정한다. 기존 집계는 `applied_at`으로 관측 마감과 주간 Elo 변화량을 판단하고, `occurred_at`의 현지 날짜로 최초 풀이·완료 일자와 스트릭을 계산한다. 정답률은 최초 풀이 기준이고 재시도는 별도 집계한다. 늦게 도착한 유효 활동은 승인 이후 조회에서 원래 학습일에 반영한다. 재현이 필요하면 `as_of`와 관측 커서를 함께 보관한다. 엔진의 `analyze_user(through_sequence=...)`는 커서 고정을 지원하므로 서비스 어댑터에서 이를 연결한다. [분석 구현](neuroknot_ml/learning_analytics.py)

**팀 합의.** 이벤트·영수증 보존 기간, 개인정보 삭제 후 중복 방지에 필요한 최소 기록과 처리 방침, 체크포인트 백업·복원 목표, 시계 허용 오차와 오프라인 제출을 정한다. 초기 온라인 전용 권장값은 서버가 받은 시각으로 활동 시각을 확정하는 것이다. 오프라인 시각을 허용할 때는 최대 지연과 노출·완료 경계를 별도로 합의한다.

## 4. 재전송·동시 요청의 트랜잭션

**현재.** 단일 서비스 인스턴스의 잠금 안에서 재전송과 유효성을 검사한다. 같은 제출 ID의 같은 선택은 완료 후에도 원래 결과를 돌려주며, 다른 선택으로 ID를 재사용하면 두 선택이 모두 오답이어도 충돌한다. [워크플로 테스트](tests/test_service_workflow.py)

**Prediction 후속.** InnoDB의 스트림 행을 직렬화 지점으로 사용한다. 공유 난이도 b를 갱신하므로 사용자별 잠금만으로는 두 사용자의 같은 문항 갱신 순서를 보장할 수 없다.

1. 요청의 형식과 인증을 먼저 확인한다. 기본 DB의 명시적 트랜잭션에서 스트림 행을 `SELECT … FOR UPDATE`로 잠근 뒤, 해당 트랜잭션의 최신 커서·영수증·노출·출판 버전을 읽는다. 잠금 전에 확정한 DB 읽기 스냅샷을 사용하지 않는다. 출판도 같은 잠금 순서를 따른다. [InnoDB 잠금 읽기](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)
2. 권한 범위 안에서 기존 영수증을 우선 조회한다. 동작, 사용자, 노출·문항·버전 및 선택값처럼 의미를 결정하는 필드가 같으면 원래 결과를 반환한다. 재요청 때 새로 부여된 서버 타임스탬프는 비교에서 제외한다. 내용이 다른 동일 키는 충돌이고, 다른 사용자의 자원은 응답에 드러내지 않는다.
3. 새 명령만 활성 버전·소유권·완료 상태·최초 풀이를 확인한다. 트랜잭션 전용 상태에 적용하고 다음 순번, 이벤트, 영수증, 업무 레코드와 모델 헤드를 같은 트랜잭션에 기록한다. 롤백 또는 중복에는 순번을 소비하지 않는다. 연속 모델 순번은 롤백 시 값이 소실될 수 있는 `AUTO_INCREMENT` 대신 잠근 커서 행에서 할당한다. [InnoDB AUTO_INCREMENT](https://dev.mysql.com/doc/refman/8.0/en/innodb-auto-increment-handling.html)
4. 커밋 뒤 응답과 새 모델 상태를 공개한다. 롤백 시 임시 객체를 폐기한다. 다중 워커 추천은 동일한 내구 헤드에서 모델·노출·카탈로그를 함께 읽는다. 이전 커서의 캐시를 사용할 경우 그 읽기 전체가 같은 커서에 묶여야 한다. 초기 구현에서는 커밋된 헤드 기준 읽기를 권장한다.
5. 교착·잠금 시간 초과는 전체 트랜잭션을 롤백하고 동일 키로 제한적으로 재시도한다. 커밋 결과가 불명확하면 기본 DB에서 영수증을 확인하고, 없으면 동일 키로 잠금 경계부터 재시도한다. 재시도 가능 상태는 앱에 공통 오류로 안내한다. [InnoDB 교착 처리](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks-handling.html)

**팀 합의.** MySQL 운영 버전·격리 수준·재시도 예산, 요청 및 영수증 보존 기간, 재시도에 필요한 인증 정보와 기한을 확정한다. 이 설계가 보장하려는 것은 같은 키에 대한 **커밋된 학습 효과의 중복 방지**다. 네트워크 전달 횟수와 화면 표시 횟수는 별개다. 스트림 잠금 대기, DB 쓰기량, 체크포인트 크기를 측정한 뒤 운영 규모를 결정한다.

## 5. Generation 검증과 채점 키

**현재.** [GeneratedQuiz 스키마](../gen/neuroknot_gen/schemas.py)는 지문 ID, 프롬프트 버전과 모델, 난이도 힌트, 세 문항과 네 선택지, 정답 인덱스·근거·해설·오답 분석을 정의한다. [Generation 검증기](../gen/neuroknot_gen/validate.py)는 실제 지문 근거 포함, 스킬·근거 중복, 정답 노출과 오답 인덱스 정합성 등을 확인한다. 서비스는 검증된 입력을 받고 슬롯별 문항 ID와 내부 채점 키를 만들며, Generation 검증 자체는 호출자의 책임이다. 초기 난이도는 명시 문항 별점 → 지문 힌트 → 중립 prior 순이다.

**Prediction 후속.** 출판 경계에서 `GeneratedQuiz` 스키마 및 `check_quiz()`를 검수 본문에 대해 실행하고, 문항 ID·버전을 부여한다. 지문 힌트에서 온 prior의 출처를 저장한다. 프롬프트 버전·모델은 추적용 메타데이터로 두고 출판 버전은 별도로 부여한다. 선택값은 저장한 원래 배열의 0~3 정수로 해석한다. 채점 키는 불변 문항 버전에 서버 전용으로 묶고 접근 권한 및 로그 제외 규칙을 적용한다. 학습된 b는 재등록으로 초기화하지 않는다.

**팀 합의.** 콘텐츠 검수·출판의 운영 주체, 버전 발급자, 수정·비활성화 절차, Generation 패키지 배포 방식과 채점 키 저장소의 접근 권한을 정한다. 기본안은 출판 경계에서 Gen 검증을 재사용하고, Prediction은 같은 출판본을 대상으로 추천·채점하는 것이다.

## 6. 해설 응답과 서버 전용 데이터

**현재.** 공개 퀴즈에는 본문·문항·선택지만 들어가며 답안 응답에는 정오답과 재시도 여부가 포함된다. 워크플로는 생성된 해설·근거·오답 분석을 보관하거나 제공하는 인터페이스가 없다.

**Prediction 후속.** 앱에서 해설이 필요하면 완료한 사용자가 같은 노출의 문항에 대해 별도로 요청하게 한다. 예시 `GET /prediction/exposures/x1/items/{item_id}/explanation` → `{"item_id":"…","explanation":"…"}`. 같은 불변 버전에 속하고 공개 검수를 통과한 해설만 필드 허용 목록으로 내보낸다. 선택한 오답에 대한 맞춤 피드백은 승인된 제출을 서버에서 찾고, 별도 검수 후 선택 기능으로 추가할 수 있다. 원시 정답 인덱스·채점 키, 내부 근거/오답 분석 원본, 모델 추적 메타데이터, 체크포인트는 서버 전용 저장·응답 모델로 분리한다.

**팀 합의.** 정답 공개의 교육적 시점, 완료 후 표시할 해설·지문 인용 범위, 화면 문구와 검수 책임을 정한다. 권장 기본안은 시도 중 정오답만 제공하고 해설은 완료 뒤 공개하는 것이다.

## 7. 추천과 실제 노출 확정의 경쟁 조건

**현재.** 추천 커서는 관측값이고 예약이 아니다. 두 추천이 같은 지문을 고를 수 있다. 한 인스턴스에서는 확정 시 활성 버전과 노출 이력을 다시 검사하므로 두 개의 다른 ID로 같은 지문을 중복 확정할 수 없다. 같은 ID의 정확한 재전송은 버전 교체 후에도 원래 결과를 돌려준다.

**Prediction 후속.** 추천에서 후보 식별자만 전달하고, 노출 확정 커밋 후 풀 퀴즈를 반환한다. 동시 요청에서 다른 ID로 같은 지문을 확정하면 첫 번째만 승인하고 다른 요청은 충돌 후 재추천하도록 한다. 추천 뒤 버전이 바뀌면 새 확정을 충돌 처리한다. 무관한 사용자 이벤트로 커서가 바뀌어도 현재 후보 조건이 유효하면 확정할 수 있다. 응답 유실 시 같은 ID를 재사용하면 원래 지문과 순번을 받는다.

**팀 합의.** 서버가 제공을 승인한 시점을 노출로 집계할지, 기기 렌더링을 별도 지표로 받을지 정한다. 기본안은 확정 커밋을 운영상 노출 시점으로 사용하고, 실제 렌더링 확인은 필요한 경우 별도 텔레메트리로 수집하는 것이다. 예약·만료는 경쟁률이나 UX 요구가 확인된 뒤 검토한다.

## 8. 인증·CORS·공통 오류 연결점

**현재.** PR #12의 참고 리비전은 앱 수명 주기, 요청 단위 DB 세션, Health 및 공통 오류 응답을 구성한다. 워크플로는 호출자로부터 사용자 ID를 받는 Python 계층이다. [PR #12의 세션 구성](https://github.com/studio-lucky7/neuroknot/blob/7cc1d9d1a87066b64aaf12fd6c736309cd553094/backend/app/db.py), [공통 오류 구현](https://github.com/studio-lucky7/neuroknot/blob/7cc1d9d1a87066b64aaf12fd6c736309cd553094/backend/app/errors.py)

**Prediction 후속.** 공통 인증 의존성에서 사용자 ID를 받고 소유권을 검증한다. DB 세션을 사용하되 커밋은 서비스 명령 경계에서 명시한다. Pydantic 요청 모델에는 엄격한 정수 `choice_index`와 허용 필드만 둔다. 도메인 실패는 공통 `code`, `message`, `issues` 형태에 매핑하고 원본 예외·제출값·채점 키를 오류에 포함하지 않는다.

| 조건 | 응답 제안 |
| --- | --- |
| 인증 없음 / 내부 출판 권한 없음 | 401 / 403. 구체 오류 코드는 공통 인증 정책을 따름 |
| 현재 사용자 범위에서 노출·문항을 찾을 수 없음 | 404 |
| 비활성 버전, 중복 노출, 동일 키의 다른 내용, 답안 누락 완료, 완료 후 새 제출 | 409. 앱이 재추천·재입력 여부를 구분할 수 있는 코드 제공 |
| 잘못된 필드·선택 범위·시각·시간대 | 422 |
| 일시적 DB 오류 또는 상태 복구 중 | 503 제안. 재전송에 동일 키 사용 |
| 정확한 재전송 / 후보 소진 | 200. 원래 응답 / 빈 추천 |

**팀 합의.** 인증 주체·권한·관리 경계, Expo Web 개발 및 운영 origin 허용 목록, 쿠키·인증 헤더 정책, 공통 오류 코드·로그 규칙을 확정한다. 자격 증명을 사용하면 명시적 origin 허용 목록을 쓰는 안을 권장한다. CORS 설정은 Expo Web과 브라우저를 위한 경계이며 서버의 인증·권한 검사와 별도로 적용한다. [FastAPI CORS 문서](https://fastapi.tiangolo.com/tutorial/cors/)

## 9. 출시 범위와 우선순위

**현재.** 등록부터 학습·분석·복원까지 Python에서 실행할 수 있고 [합성 워크플로 데모](scripts/run_service_workflow.py)가 있다.

**Prediction 후속.** P0는 검수된 퀴즈 출판, 내구 저장·복구, 추천·노출·제출·완료·분석이다. P1은 완료 후 해설과 운영용 출판 API다. P2는 오프라인 시각·렌더링 이벤트·예약·재학습과 주기 체크포인트 최적화다. 모델 변경 없이 먼저 단일 스트림으로 회귀를 확인한다.

**팀 합의.** 앱 출시 필수 화면, 해설 출시 시점, 사용자에게 재시도를 허용하는 기간, 분석 범위·데이터 보존 정책, P0 부하 기준을 확정한다.
